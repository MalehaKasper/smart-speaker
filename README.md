# 🔊 Smart Speaker 2.1

**Монорепозиторій колонки: прошивка ESP32 + мобільний додаток керування.**

Дві частини одного пристрою, що спілкуються по BLE та живуть в одному репозиторії саме тому, що протокол між ними має завжди лишатись синхронізованим: коли фіча (наприклад, новий тип фільтра EQ) торкається обох сторін, вона планується й мержиться **одним PR**, а не двома окремими, які можуть розійтись.

- [`firmware/`](firmware/README.md) — ESP-WROOM-32 (PlatformIO, C++): A2DP Sink → I2S, BLE GATT-сервер, керування ADAU1401 через Safeload, енкодер/ІЧ, TM1650, WS2812B VU-метр, NVS
- [`app/`](app/README.md) — Flutter: BLE-клієнт, FFT-аналіз для рум-корекції, калькулятор biquad-коефіцієнтів, UI гучності/EQ

## 🔌 Протокол (спільний контракт)

BLE GATT, control-характеристика (write) + notify-характеристика:

| Payload | Значення |
|---|---|
| `0x01 [0-100]` | Гучність |
| `0x02 [0/1]` | Джерело: 0 = Bluetooth, 1 = AUX |
| `0x03 [байти]` | Коефіцієнти біквадратних фільтрів EQ |

Прошивка приймає й декодує ці байти в `firmware/src/ble_server.cpp`; додаток формує й надсилає їх у `app/lib/ble/`. Зміна формату — це одна зміна в `openspec/changes/`, що зачіпає обидві сторони одночасно.

## 📐 Планування (OpenSpec)

`openspec/changes/` містить дві початкові зміни — `build-firmware` і `build-mobile-app` — кожна зі своїм proposal/design/specs/tasks. Нова спільна фіча (наприклад, "новий тип фільтра EQ") оформлюється як **одна** зміна з capabilities по обох сторонах, щоб конфлікти між прошивкою й додатком (формат байтів, ліміти буфера, MTU) виявлялись на етапі `design.md`, до написання коду.

```bash
openspec status --json          # стан поточних змін
```

## 🛠 Розробка

```bash
cd firmware && pio run          # збірка прошивки
cd app && flutter run           # запуск додатка
```
