## Context

`build-firmware` дав робочий каркас, але не враховує реальні часові обмеження ESP32: радіостек (BLE+A2DP) чутливий до затримок, а поточний код виконує I2C/LED/NVS-роботу прямо в BLE-колбеках. Ця зміна не додає нової зовнішньої поведінки — вона робить існуючу поведінку (аудіо без заїкань, BLE без розривів) справджуваною на реальному залізі.

## Goals / Non-Goals

**Goals:**
- Жодна дія, ініційована BLE/IR/енкодером, не виконує I2C/NVS/LED-роботу в контексті радіостека
- Зміна гучності/EQ з додатка не спричиняє чутних заїкань паралельного A2DP-потоку
- Прошивка не звертається по I2C до ADAU1401, поки Selfboot не завершився
- IR і WS2812B використовують апаратні периферали (RMT), а не програмний bit-bang, вразливий до переривань радіостека

**Non-Goals:**
- Зміна протоколу BLE чи формату EQ-даних (це `build-firmware`/`build-mobile-app`, не чіпається)
- Реалізація level shifter чи розв'язки живлення в коді — це апаратні вимоги до плати, фіксуються як примітки, не як завдання прошивки
- Вимірювання реальної затримки/джитеру на залізі (це подальша перевірка, не частина цієї зміни — заліза ще немає)

## Decisions

- **FreeRTOS-черга команд + задача на Core 1**: BLE write-колбеки (`ble_server.cpp`), колбеки енкодера й IR (`inputs.cpp`) кладуть структуру-команду (тип + payload) у чергу (`xQueueSend`, з ISR-варіантом `xQueueSendFromISR` там, де колбек викликається з переривання) замість виклику `DspController`/`Display`/`LedStrip`/`Storage` напряму. Окрема задача, створена через `xTaskCreatePinnedToCore(..., 1)`, читає чергу в `loop()`-подібному циклі й виконує всю "важку" роботу. Причина: ізолює час виконання I2C/NVS/LED від часу виконання радіостека без здогадок про те, на якому ядрі Arduino-фреймворк фактично розміщує BLE-колбеки.
- **Selfboot-очікування як фіксована затримка з можливістю подальшого уточнення**: перед першим зверненням `DspController::begin()` до I2C — витримати паузу (орієнтовний час — з даташиту ADAU1401, поки не підтверджено; тимчасово консервативне значення) або, якщо ADAU1401 виставляє готовність через GPIO/статус-регістр, перевірити цей сигнал замість сліпої затримки. Остаточний механізм залежить від того, що покаже реальна плата — зафіксовано як Open Question нижче.
- **Явний build-flag для FastLED RMT-бекенду**: не покладатись на бекенд за замовчуванням; явно увімкнути RMT5-драйвер (чи актуальний для версії 3.7.0 еквівалент) у `platformio.ini`, щоб оновлення стрічки не деградувало до bit-bang під навантаженням.
- **IRremote v4 на RMT приймається як уже задоволене, з перевіркою**: бібліотека `IRremote @ ^4.4.0` на платформі ESP32 за замовчуванням використовує RMT-периферію. Явного build-flag не додаємо, але зберігаємо задачу підтвердити це при першій збірці (лог/документація бібліотеки), а не вважати аксіомою.
- **Апаратні вимоги фіксуються як примітки в README/design, не як завдання прошивки**: level shifter для WS2812B і розв'язка живлення PAM8403 — це рішення про монтаж плати, які потрібно не забути, але вони не мають відповідного тестованого коду.

## Risks / Trade-offs

- [FreeRTOS-черга додає непряму затримку (команда виконається на наступній ітерації задачі Core 1, не миттєво в колбеку)] → Затримка вимірюється мілісекундами за нормальної частоти циклу задачі — прийнятно для гучності/EQ; якщо стане відчутною, зменшити період очікування задачі на черзі.
- [Точний час Selfboot ADAU1401 невідомий без даташиту/спостереження на залізі] → Почати з консервативної затримки (напр. 100-200 мс) і скоротити після спостереження реальної поведінки; якщо ADAU1401 дає статус-сигнал готовності — перейти на нього замість сліпої затримки.
- [FASTLED_RMT5 (чи потрібний build-flag) може відрізнятись між версіями FastLED/ESP-IDF, використаними PlatformIO] → Перевірити фактичну версію ESP-IDF, з якою збирається `platform = espressif32`, і звірити з документацією FastLED для цієї комбінації перед фіксацією конкретного флага.
- [Черга й задача на Core 1 — новий шар складності в коді, який раніше був простим лінійним `loop()`] → Виправдано вимогою надійності аудіо/BLE; тримати логіку задачі максимально простою (switch по типу команди), без додаткової бізнес-логіки всередині обробника черги.

## Open Questions

- Чи ADAU1401 на цій платі має апаратний сигнал готовності після Selfboot (GPIO/статус-регістр), чи потрібна лише затримка за часом? Потребує даташиту або спостереження на реальній платі.
- Точний build-flag FastLED для RMT-бекенду на версії 3.7.0 з ESP-IDF, яку тягне `platform = espressif32` в поточному `platformio.ini` — потребує перевірки під час першої реальної збірки.
